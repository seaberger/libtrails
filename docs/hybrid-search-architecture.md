# Hybrid Search Architecture

LibTrails uses a 7-signal hybrid search system that combines full-text keyword search (FTS5) with semantic vector search (sqlite-vec) via Reciprocal Rank Fusion (RRF). This document describes the architecture, the signals, the data tables, and the fusion algorithm.

## Overview

The search system answers the question: *"Given a user query, which books are most relevant?"* It attacks this from multiple angles — keyword matches in titles, semantic similarity across 837K extracted topics, 7K LLM-generated book themes, 335K text chunks, and whole-book metadata vectors — then fuses the results into a single ranked list.

```text
User Query: "dystopian fiction"
        │
        ├──► FTS5 keyword search (3 signals)
        │    ├── books_fts:  title, author, description, series, themes
        │    ├── topics_fts: 837K normalized topic labels
        │    └── chunks_fts: 335K text chunks → mapped to books
        │
        ├──► Semantic vector search (4 signals)
        │    ├── topic_vectors:      837K topic embeddings → mapped to books
        │    ├── book_theme_vectors:  7K theme embeddings → mapped to books
        │    ├── book_vectors:        926 whole-book embeddings
        │    └── chunk_vectors:       335K chunk embeddings → mapped to books
        │
        └──► Reciprocal Rank Fusion (k=60)
             └── Final ranked list: [(book_id, rrf_score)]
```

## The 7 Search Signals

### Signal 1: FTS Book Metadata (`fts_books`)

**What it searches**: Title, author, description, series name, and LLM-generated book themes (the `book_themes` JSON column).

**How it works**: FTS5 with porter stemmer tokenizer. The query is sanitized (special characters stripped), tokens are OR-joined, and BM25 scoring ranks results.

**When it shines**: Direct title/author matches. Searching "Hunger Games" or "Orwell" hits immediately.

| Detail | Value |
|--------|-------|
| Table | `books_fts` (FTS5 virtual table) |
| Columns | `title, author, description, series, themes` |
| Tokenizer | `porter unicode61` |
| Scoring | BM25 (negated — FTS5 returns negative values) |
| Candidate limit | 50 |
| Code | `hybrid_search.py:_fts_search_books()` |

### Signal 2: FTS Topic Labels (`fts_topic_books`)

**What it searches**: 837K normalized topic labels extracted from book chunks by the V2 pipeline (gemma-3-27b themes + gemma-3-12b chunk topics).

**How it works**: FTS5 keyword search on `topics_fts`, then maps matching topic IDs to books via `chunk_topic_links → chunks → books`. Best score per book is kept.

**When it shines**: When the user's query terms appear literally in extracted topics. E.g., "machine learning" matches topics like "machine learning optimization techniques".

| Detail | Value |
|--------|-------|
| Tables | `topics_fts` → `chunk_topic_links` → `chunks` → `books` |
| Candidate limit | 100 topics → mapped to books |
| Code | `hybrid_search.py:_fts_search_topics()` + `_topics_to_books()` |

### Signal 3: FTS Chunk Content (`fts_chunk_books`)

**What it searches**: The raw text of 335K book chunks (~500 words each).

**How it works**: FTS5 keyword search on `chunks_fts`, then aggregates to books by keeping the best BM25 score per book.

**When it shines**: Specific phrases, names, or terms that appear in book content but not in metadata or topic labels. E.g., searching for a character name.

| Detail | Value |
|--------|-------|
| Tables | `chunks_fts` → `chunks` → `books` |
| Candidate limit | 200 chunks → aggregated to books |
| Code | `hybrid_search.py:_fts_search_chunks()` |

### Signal 4: Semantic Topic Search (`sem_topic_books`)

**What it searches**: 837K topic embedding vectors (BGE-small-en-v1.5, 384 dimensions) via cosine similarity.

**How it works**: The query is embedded, then searched against `topic_vectors` using sqlite-vec's approximate nearest neighbor search. Matching topics are mapped to books via `chunk_topic_links → chunks`. This is the **dominant semantic signal** — it consistently surfaces the most unique books because the topic vocabulary is so large (837K labels).

**When it shines**: Conceptual queries where the user's words differ from exact topic labels. "Authoritarian government" finds topics about "totalitarian regimes", "state surveillance", "political oppression".

| Detail | Value |
|--------|-------|
| Tables | `topic_vectors` → `topics` → `chunk_topic_links` → `chunks` → `books` |
| Embedding model | BAAI/bge-small-en-v1.5 (384 dims) |
| Distance metric | Cosine |
| Candidate limit | 200 topics → mapped to books |
| Code | `hybrid_search.py:_semantic_search_topics()` + `_topics_to_books()` |

### Signal 5: Semantic Book Themes (`sem_theme_books`)

**What it searches**: 7,061 book theme embedding vectors. These themes were generated by gemma-3-27b as high-level descriptors per book (e.g., "dystopian young adult fiction", "Renaissance art history").

**How it works**: The query is embedded, searched against `book_theme_vectors`, then results are joined through `book_theme_entries` to get book IDs. Best similarity per book is kept. This acts as a **lightweight ColBERT/MaxSim pattern** — each book is represented by multiple theme vectors, and the best-matching theme determines the book's score.

**When it shines**: Broad genre/theme queries. "Dystopia" matches theme labels like "dystopian young adult fiction" even when the word doesn't appear in the title.

| Detail | Value |
|--------|-------|
| Tables | `book_theme_vectors` → `book_theme_entries` → `books` |
| Source data | `books.book_themes` (JSON array from 27b extraction) |
| Embedding model | BAAI/bge-small-en-v1.5 (384 dims) |
| Distance metric | Cosine |
| Candidate limit | 50 |
| Code | `hybrid_search.py:_semantic_search_book_themes()` |

### Signal 6: Semantic Whole-Book Vector (`sem_book_direct`)

**What it searches**: 926 book-level embedding vectors, each constructed from a concatenation of the book's title, author, description (first 150 words), and theme labels.

**How it works**: A single 384-dim vector per book captures the book's overall "vibe". The query is embedded and compared directly to these book vectors. No join or aggregation needed — each vector already represents a book.

**Why not average chunk embeddings?** Mean-pooling hundreds of chunk embeddings dilutes signal. A 400-page novel about war would average out to a generic "fiction" vector because most chunks contain dialogue, scene-setting, and character development — not the core themes. The title+description+themes approach captures the book's identity in a compact, purpose-built representation. (See: Gunther et al., "Late Chunking", 2024; Arora et al., ICLR 2017 on random-walk sentence embeddings.)

**When it shines**: Holistic queries that match a book's overall identity. "Epic fantasy series" ranks Lord of the Rings, Wheel of Time, Mistborn highly because their descriptions and themes align.

| Detail | Value |
|--------|-------|
| Table | `book_vectors` |
| Source data | `title + " by " + author + ". " + description[:150 words] + ". Themes: " + themes` |
| Embedding model | BAAI/bge-small-en-v1.5 (384 dims) |
| Distance metric | Cosine |
| Candidate limit | 50 |
| Code | `hybrid_search.py:_semantic_search_books_direct()` |
| Build function | `vector_search.py:rebuild_book_vector_index()` |

### Signal 7: Semantic Chunk Content (`sem_chunk_books`)

**What it searches**: 335,010 chunk embedding vectors — every ~500-word block of text from every parsed book, embedded as a 384-dim vector.

**How it works**: The query is embedded and searched against `chunk_vectors`. Results are joined through `chunks` to get book IDs, with the best similarity per book kept.

**When it shines**: Narrative/fiction queries where the actual prose captures the concept better than metadata. "Dystopia" finds books with dystopian scenes even if the word doesn't appear in the title or themes. Also useful for very specific factual queries where a particular passage is uniquely relevant.

**Trade-off**: This signal has the **highest overlap** with other signals — most books it finds are already found by topic or book vectors. Its exclusive contribution is modest (2-15 books per query) but serves as a safety net for content-level matches that metadata misses.

| Detail | Value |
|--------|-------|
| Tables | `chunk_vectors` → `chunks` → `books` |
| Embedding model | BAAI/bge-small-en-v1.5 (384 dims) |
| Distance metric | Cosine |
| Candidate limit | 100 |
| Storage | ~500 MB |
| Code | `hybrid_search.py:_semantic_search_chunks()` |
| Build function | `vector_search.py:rebuild_chunk_vector_index()` |

## Reciprocal Rank Fusion (RRF)

### The Algorithm

RRF combines multiple ranked lists into a single ranking without needing to normalize scores across different systems. Each signal produces a list of `(book_id, score)` pairs sorted by score descending. RRF ignores the raw scores and uses only rank position:

```python
def rrf_fuse(ranked_lists, k=60):
    scores = {}
    for ranked in ranked_lists:
        for rank, (item_id, _score) in enumerate(ranked):
            scores[item_id] = scores.get(item_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)
```

For a book at rank `r` in signal `s`, its contribution is `1 / (k + r + 1)`. The `k=60` parameter (from Cormack, Clarke & Buettcher, 2009) controls how much rank position matters — higher k dampens the difference between rank 1 and rank 10.

### Why RRF Works Well Here

1. **Score incompatibility**: BM25 scores (FTS5) and cosine similarities (sqlite-vec) are on completely different scales. RRF sidesteps this by using rank order only.

2. **Robustness to noise**: A weak signal can't hurt much. If `sem_chunk_books` ranks an irrelevant book at position 50, it contributes only `1/(60+51) = 0.009` — negligible.

3. **Reward for consensus**: A book ranked in the top 10 by 4 different signals gets a much higher fused score than a book ranked #1 by only one signal. This naturally surfaces books with broad relevance.

4. **No tuning required**: Equal-weight RRF with k=60 is the standard default. The implicit weighting comes from candidate pool sizes — `sem_topic_books` (200 candidates) naturally contributes more than `sem_book_direct` (50 candidates).

### Signal Contribution Analysis

Diagnostic analysis across 6 query types (dystopia, machine learning, cooking/food, quantum physics, dragons/magic, stoicism/ancient philosophy):

| Signal | Avg Candidate Pool | Avg Exclusive Books | Role |
|--------|-------------------|-------------------|------|
| `sem_topic_books` | ~100 | ~35 | Dominant semantic signal, largest unique contribution |
| `sem_book_direct` | ~50 | ~19 | Strong holistic signal, captures book "vibe" |
| `sem_chunk_books` | ~30 | ~8 | Safety net for content-level matches |
| `sem_theme_books` | ~25 | ~8 | Theme-level matching (27b labels) |
| `fts_chunk_books` | ~40 | ~7 | Specific factual content keyword matches |
| `fts_books` | ~15 | ~5 | Essential for exact title/author hits |
| `fts_topic_books` | ~20 | ~4 | Topic label keyword matches |

"Exclusive books" = books found only by that signal and no other.

## Database Tables

### FTS5 Tables (Keyword Search)

| Table | Source | Columns | Tokenizer |
|-------|--------|---------|-----------|
| `books_fts` | `books` | title, author, description, series, themes | porter unicode61 |
| `topics_fts` | `topics` | label | porter unicode61 |
| `chunks_fts` | `chunks` | text | porter unicode61 |

### sqlite-vec Tables (Semantic Search)

| Table | Source | PK Column | Vectors | Size |
|-------|--------|-----------|---------|------|
| `topic_vectors` | `topics.embedding` | topic_id | 837,320 | ~1.2 GB |
| `book_theme_vectors` | `book_theme_entries` | theme_id | 7,061 | ~10 MB |
| `book_vectors` | computed from book metadata | book_id | 926 | ~1.4 MB |
| `chunk_vectors` | `chunks.text` | chunk_id | 335,010 | ~490 MB |

All vec0 tables use `FLOAT[384] distance_metric=cosine`.

### Supporting Tables

| Table | Purpose | Key Columns |
|-------|---------|-------------|
| `book_theme_entries` | Parsed themes from `books.book_themes` JSON | id, book_id, theme |
| `chunk_topic_links` | Many-to-many: chunks ↔ normalized topics | chunk_id, topic_id |
| `topics` | Normalized, deduplicated topic labels with embeddings | id, label, embedding, cluster_id |
| `chunks` | ~500-word text blocks from parsed EPUBs | id, book_id, text |

## Match Type Labels

When results are returned to the frontend, each book gets a `match_type` label indicating the **primary** signal that found it (checked in priority order):

| Priority | match_type | Meaning |
|----------|-----------|---------|
| 1 | `keyword` | Found by FTS on book metadata (title/author/description/themes) |
| 2 | `book` | Found by whole-book semantic vector |
| 3 | `theme` | Found by book theme vector (MaxSim pattern) |
| 4 | `content` | Found by FTS on chunk text |
| 5 | `chunk_semantic` | Found by semantic search on chunk vectors |
| 6 | `semantic` | Found by semantic search on topic vectors → books |
| 7 | `topic` | Fallback (topic-mapped) |

Note: A book may appear in multiple signals. The match_type reflects the highest-priority signal, not the only one. The RRF score reflects contributions from all signals.

## CLI Commands

```bash
# Rebuild FTS indexes (includes book_themes in books_fts)
uv run libtrails rebuild-fts

# Embed topics only (default)
uv run libtrails embed

# Embed book themes → book_theme_vectors (~3 seconds)
uv run libtrails embed --themes

# Embed books (title+desc+themes) → book_vectors (~7 seconds)
uv run libtrails embed --books

# Embed chunks → chunk_vectors (~30-40 minutes on Apple Silicon)
uv run libtrails embed --chunks

# Embed everything
uv run libtrails embed --all
```

## Graceful Degradation

All semantic search functions wrap their vec0 queries in try/except blocks, returning an empty list if the vector table doesn't exist or isn't populated. This means the search system works at any stage of the build process:

- **No vectors built**: Pure FTS search (signals 1-3 only)
- **Topics only**: FTS + topic semantic (signals 1-4)
- **Full build**: All 7 signals active
